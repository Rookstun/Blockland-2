- CONST ARRAY LIMIT (2026-11-07, ROTOR RAID): a wirescript `const X = [...]` with more than a few thousand entries (4096 chunks still failed; 1000-entry chunks now, untested) compiles but reading past index ~4096 fails at runtime (no log error): the rows using those entries came out empty (len 0) and the bottom of the picture vanished. Keep const tables <= 4000 and chunk bigger ones (rotorraid channel: MP0/MP1 + mod mp(j)). Also seen: per-chip logs via PrintToConsole show up as "LogBrickadia: [Wire Graph] <text>".
- SHARED TICK BUDGET (2026-11-07, ROTOR RAID debug prints): the wire/script work budget is shared by ALL chips in one server tick. With 10 render channels on one Change(frame), ch0-3 drew, ch4 stopped mid-strip and ch5-9 never entered row() (their mod calls failed silently, cheap statements and PrintToConsole after still ran: len 0 strips). More objects (tanks) = budget gone sooner = "bottom half vanishes". Fix: spread the work over ticks (rotorraid: a phase_ wire, channel k draws on phase floor(k*3/NCH) of a 3-tick frame). The earlier "const array limit" guess was probably this too.
- FASTER CLOCK = MORE BUDGET (2026-11-07, Rookstun on ROTOR RAID): running the cabinet clock faster than 20 Hz gives more ticks per second, each with its own shared budget, so the 3-phase drawing finishes and frames load with no dropped pixels. Catch: game logic stepped per tick speeds up too. Proper form: faster clock for phases/drawing + game steps scaled by real time (ServerUptime delta, as Night Pong does with kt), or step the game every Nth tick.
